# Independent review of mobile phase 2 (882c572..b308238)

Date: 2026-11-04. Reviewer: independent verifier (did not write this code). Reviewed at b308238.
Inputs: `docs/MOBILE_ARCHITECTURE.md`, `docs/CONTRACT.openapi.yaml` (/runs, /reports, /live), `docs/compliance/*`, `docs/verification/M-phase2.md`, and every file under `mobile/lib`, `mobile/test`, `mobile/tool`, `AndroidManifest.xml`.

How this was done, and its limits: there is no Flutter or Dart SDK here, so nothing was compiled or run. CI compiles and tests the code (green on dce470c), so this review looks for what CI cannot catch. Every finding below comes from reading the code against the contract. Blocker 1 depends on Dart `async*` cancellation semantics, which I know well but did not run; the fix includes a test that proves it either way. I tried to read the flutter_foreground_task sources for `stopWithTask` and the task-data callback, but WebFetch was blocked by the session allowlist, so those plugin semantics are unverified beyond "it compiles in CI". I did not check go_router 17, maplibre_gl or drift APIs beyond what CI proves.

## Verdict: accepted-with-fixes

The recorder core is sound. Fixes are written before the recorder or the UI see them. `stopping` is a real state that waits for in-flight writes. Crash recovery covers `recording` and `paused` runs and never claims the run of the current process. The `/live` token goes in the first message and not in the URL. `ACCESS_BACKGROUND_LOCATION` is absent and the check script cannot pass vacuously. The disclosure strings match `location-disclosure.md` exactly (compared programmatically: collect, why, when, sharing with the placeholder, control). The architecture rules hold in the imports I read.

Four things must be fixed before Gate 1 (the device test): a socket leak in `/live`, local runs and home zones that are not tied to an account, 401 handling in the upload queue, and tests that would stay green if the two main data-loss guards were deleted.

## Blockers (must fix)

### B1. `/live` socket is not closed when the subscription is cancelled (socket leak, exhausts the 5-socket cap)

- `mobile/lib/data/services/live_service.dart:43-63` (`connect` is an `async*` generator with an inner `await for (... in socket)`), used by `cell_repository.dart:99-106` (`stopLive`), `:108-141` (`_connect`, which cancels the previous subscription) and `ui/map/map_view_model.dart:75-79` (dispose).
- Failure scenario: cancelling a subscription to an `async*` stream does not interrupt a generator that is suspended in an `await` of its own. The body only notices the cancel at its next `yield`. Here the generator sits in `await for` over the socket, and the only `yield` is a parsed `cell_changed` frame. So after the user leaves the Map tab, or pans (which makes `_connect` cancel the old subscription and open a new one), the old socket stays open until the next `cell_changed` arrives for that old bbox, which may be minutes or never. The contract allows 5 concurrent sockets per user and closes the 6th with 4429. A user who pans around a quiet area five times has all slots held by dead sockets. After that every new connection gets 4429, which `CellRepository` treats as an ordinary drop and retries forever with backoff, so live updates are dead for the session. It also keeps a radio and a token-authenticated connection open after the map is gone. The same leak happens on the 15 s connect timeout (line 44): the `timeout` fires but the underlying `WebSocket.connect` may still complete later and is never closed.
- `FakeLiveService` uses a plain `StreamController`, so no test can see this.
- Fix: build the stream with a `StreamController<CellChange>` whose `onCancel` closes the socket (and whose `onListen` starts the connect). Keep the socket in a variable the cancel path can reach. For the timeout use `HttpClient()..connectionTimeout = Duration(seconds: 15)` passed as `customClient`, or close the socket in a `.then` if the timeout already fired. Add a test with a local `HttpServer` + `WebSocketTransformer` (dart:io works under `flutter test`) that asserts: (a) the first frame received is `{"type":"auth","token":...}` and the request URI contains no `token`; (b) after `subscription.cancel()` the server side sees the socket close within a short time without sending any frame; (c) a server close with code 4401 surfaces as `LiveClosedException(4401)`.

### B2. Local runs, fixes and home zones are not tied to an account and survive sign-out

- `data/db/app_database.dart:9-19` (`Runs` has no user column), `:108` (`activeUploads` returns every queued job), `data/repositories/profile_repository.dart:12,49,61,67-80` (home zones in one global SharedPreferences key, and `addZoneHere` re-PUTs the whole stored list), `data/repositories/auth_repository.dart:73-77` (`signOut` clears only the token), `ui/run/run_screen.dart:245-` (`_RecentRuns` lists every finished run), `ui/home/home_screen.dart:26-60` (recovery dialog offers any unfinished run). Only `deleteAccount` wipes (`profile_repository.dart:95-99`).
- Failure scenario: user A records a run and signs out (Profile > Sign out, the disclosure's "No thanks, sign out", or the automatic sign-out after a 401), then user B signs in on the same phone (or A signs in with another Google account). The upload ticker picks A's queued run and uploads it with B's token, so A's raw GPS track is attributed to B's account and can claim cells for B. B sees A's runs in "recent runs" and the result screen, and is offered A's unfinished run in the recovery dialog. A's home-zone centres (their home address) show in B's Profile, and B's next "add zone" PUTs A's zones into B's server account. This is a raw-GPS and home-location leak between accounts and a fairness hole.
- Do not fix this by wiping on sign-out: a 401 auto sign-out must keep unsent runs for the same user (see B3).
- Fix: store `user_id` on each run row (set from the current session in `createRun`, schema version 2 with a migration that backfills nothing or the stored last user). Filter `activeUploads`, `watchRecentRuns`, `unfinishedRun` and `runById` by the signed-in user. Key the home-zone preference by user id (`home_zones_v1_<userId>`). On sign-in as a different user than the last stored one, do not delete the other user's runs silently; either keep them invisible and un-uploadable, or ask. Add tests: two users on one `MemoryStore`, user B never uploads or sees A's run; zones are per user.

### B3. A 401 permanently fails queued uploads and can sign the user out right after a run

- `data/upload/backoff.dart:36-40` (401 is not retryable), `data/upload/upload_queue.dart:105-120,143-157` (`_onError` marks the job `failed`), `data/providers.dart:68-79` (`onUnauthorized` ignores a 401 only while `isRecording`, otherwise `expireSession()` signs out), `data/services/api_service.dart:62`, `data/repositories/run_repository.dart:233` (`stop()` ends with `tickUploads()`).
- Failure scenario 1 (normal expiry, JWT TTL is 30 days per `server/app/config.py`): the user finishes a run. `stop()` sets `isRecording` false and immediately starts the upload; the server returns 401; `expireSession()` signs the user out and the router replaces the result screen with sign-in. The run's job is now `failed` with "invalid or expired token", so after signing in again the run shows "upload failed" and is retried only if the user finds it in the recent-runs list and taps retry. The run is safe on the phone, but the experience is a lost-looking run after every token expiry.
- Failure scenario 2: while a run is recording, the 5-second ticker uploads an older run, gets 401 and, because `isRecording` is true, does nothing, but the older job is still marked `failed`.
- The `isRecording` guard lives in an inline closure in `providers.dart`. Tests override `apiServiceProvider`, so this logic has no test at all.
- Fix: treat 401 (and 403 "account being deleted" is terminal, leave it) as "auth blocked" in `UploadQueue`: leave the job `queued`, do not increase `attempts`, set `nextAttemptAt` to now and stop the tick (return early) so the other jobs do not each burn a request. Resume when the session changes (the ticker or `AuthRepository.changes` triggers `tick`). Move the "do not sign out while recording" rule out of the provider closure into `AuthRepository` or `RunRepository` (for example `expireSession` is deferred until the run is stopped, and then never races with the result screen) and unit test it. Add tests: 401 on upload keeps the job queued and uploads after re-auth; 401 while recording does not sign out; 401 after stop signs out once.

### B4. The tests would stay green if the two main data-loss guards were removed, and the live socket has no test

- Mutation reasoning (each change below leaves every test in `mobile/test` passing):
  - Delete `await Future.wait(List<Future<void>>.of(_pending));` at `run_repository.dart:205`. `MemoryStore.addFix` (`test/fakes/fakes.dart:214`) completes in a microtask, and every test calls `settle()` before `stop()`, so no write is ever in flight when `stop()` runs. The `stopping` wait, the main reason that state exists, is never exercised.
  - Swap the order so the recorder and snapshot update before `_store.addFix` (lines 145-158). The test named "fixes are written to the store before they count" (`test/data/run_repository_test.dart:58`) only checks that after `settle()` both the store and the path have 2 fixes. It does not check order. The write-failure test (`:84`) does check that a failed write is not counted, which is good, but nothing pins write-before-UI.
  - `SocketLiveService` (the only code that sends the first-message auth and parses close codes) has no test. `cell_repository_test.dart` covers only reconnect logic on a fake.
  - `map_view_model_test.dart:88` is named "zooming out clears cells and closes the socket" but never asserts the socket closed (no check of `liveWanted` or the fake socket).
  - `auth_view_model_test.dart:84` ("a lost session (401) signs the user out") calls `expireSession()` directly, so it does not test the 401 path.
- Fix: give `MemoryStore` a `Completer`-based slow-write mode. Tests: (1) emit a fix with a slow write, call `stop()`, assert the run is not marked finished until the write completes and that the fix is in the uploaded payload; (2) with a slow write, assert `current.path` is empty and `distanceM` is 0 until the write completes; (3) a write that never completes before stop does not hang `stop()` forever (decide the intended behaviour and test it). Add the `SocketLiveService` tests from B1. Assert the socket is closed in the map test (`expect(repo.liveWanted, isFalse)` and the fake socket has no listener).

## Follow-ups (should fix; none blocks Gate 1 except where noted)

### Recorder and run lifecycle

- F1. Run screen shows Start while the run is `stopping`. `ui/run/run_screen.dart:77` uses `isActive` (recording or paused only), so for the moment between Stop and finish the button row flips back to Start and a tap is silently ignored (`run_repository.dart:87`, `isRecording` is true). Show a disabled "Saving..." state for `RecorderStatus.stopping`.
- F2. GPS stream errors and completion are not handled. `run_repository.dart:115` passes `onError` that only sets a message (`:166`) and has no `onDone`. If the user switches location off or revokes permission mid-run, the geolocator stream may end; the recorder stays `recording` with health `lost` forever and nothing resubscribes or tells the user to fix it. At minimum: on stream end or a `LocationServiceDisabledException`, set a clear persistent error and offer Stop; ideally resubscribe when the service is re-enabled. Also, an approximate-only location grant (Android 12+) passes `requestLocation` (`permission_service.dart:23-24`) but gives fixes with accuracy over 50 m that never count; detect and explain.
- F3. Pause keeps the GPS stream running and the notification says "Recording your run". `_onFix` drops fixes while paused (`run_repository.dart:142`) but the radio stays on, and `_tick` (`:170-178`) only maps GPS health to text, so a paused run's notification does not say paused. Either cancel and resubscribe the stream on pause/resume or update the notification text to "Paused" (and say so in the disclosure's "When" if the stream stays on).
- F4. Notification permission denied (Android 13+): the service still runs but no notification and no Stop button appear (`permission_service.dart:29-34` swallows the result). The disclosure promises "Looprun shows a notification". Check the result and tell the user on Start, or block Start.
- F5. Race between recovery and a quick Start. `findUnfinishedRun` (`run_repository.dart:267-275`) checks `isRecording`, then awaits `stopIfRunning()`. If the user taps Start during that await and the new service is already running when `isRunningService` is evaluated, the new run's service is stopped (`foreground_service.dart` `stopIfRunning`). The window is milliseconds on the first frame; cheap fix: remember a "recovery pending" flag, or have `start()` await the recovery future.
- F6. `stopWithTask: true` (`foreground_service.dart:52`) means swiping the app out of recents ends the service, and the Dart engine with the recorder dies with the activity. Crash recovery handles the data (good), but the user-visible behaviour ("my run stopped when I swiped the app away") should be a named Gate 1 test case and be stated in the tester guide. I could not read the plugin source to confirm the exact `stopWithTask` semantics.
- F7. Signing out or deleting the account while a run is active. `ui/profile/profile_screen.dart:122` signs out with no check; recording continues with no UI except the notification. `deleteAccount` then `wipe()` deletes the table the recorder is still writing to. Block both while `isRecording`, or stop the run first.
- F8. `stop()` can leave the recorder in `stopping` forever if `_teardown()` throws before `_recorder.finish()` (lines 203-208): `isRecording` stays true and the user cannot start another run until the process restarts. Wrap teardown in try/finally.

### Upload queue

- F9. Network failures give up after about 24 minutes. `BackoffPolicy` default (2 s doubling, 5 min cap, `maxAttempts` 12) sums to roughly 24 minutes of consecutive failures with the app open, after which the job is `failed` and needs a manual retry. For `statusCode == null` (no network) and 5xx the queue should not give up; use `maxAttempts` only for server answers.
- F10. 413 for runs over 20000 fixes (contract) is a permanent failure. At 1 Hz that is about 5.5 hours, rare but real for a very long run or a forgotten pause; consider decimating on upload (keep first/last, drop points within the same second) or splitting.
- F11. The ticker only runs while the Home screen is mounted (`providers.dart` `uploadTickerProvider`, `home_view_model.dart` `uploadSyncProvider`). Documented as by design; just make sure the tester guide says uploads happen when the app is open.

### `/live`

- F12. No resync after a reconnect, and a gap before the first subscription. `CellRepository._connect` (`cell_repository.dart:108-141`) never reloads the area, so changes during a dropped connection are missed until the next camera idle. `map_view_model.dart:123` also starts the socket after the REST load, so changes in between are missed. Fix: on each (re)connect call `loadArea(_liveBbox)` once, or connect first and then load.
- F13. Backoff counter only resets on a received frame (`cell_repository.dart:120`). A connection that stays up for hours without a change and then drops continues from the old failure count (up to the 2 minute cap). Reset on the first successful message or on connect time; this needs the service to expose "connected" (or an auth acknowledgement, which the contract does not have).
- F14. A handshake `403` (bad bbox, user being deleted, over 5 sockets) arrives as a `WebSocketException`, is not a `LiveClosedException`, and is retried forever with backoff. Treat repeated handshake failures as terminal until the next bbox change or app resume.
- F15. No keepalive and no lifecycle handling. `WebSocket.pingInterval` is not set (`live_service.dart:44`), so a half-open connection after a network switch is not detected by the client. The map does not observe app lifecycle: with the Map tab open and the app backgrounded, the socket and the reconnect loop continue (the OS will eventually kill the socket, then the loop retries every up to 2 minutes). Set `socket.pingInterval = Duration(seconds: 30)` and pause live updates on `AppLifecycleState.paused`.
- F16. 4401 stops live until the next camera move, and every later camera idle reconnects and gets 4401 again (`startLive` sees `_liveBbox == null`). Harmless but noisy; set a flag cleared only on a new session.
- F17. Map redraw is clear-all then add-all for every frame and every REST reload (`ui/map/map_screen.dart:249-250`). With about 0.19 degree boxes this can be thousands of circles per `cell_changed`. Move to a GeoJSON source and update features. Not urgent while volumes are low.

### Privacy, disclosure and docs

- F18. Privacy Policy "link" only shows the URL as selectable text in a dialog (`ui/disclosure/disclosure_screen.dart:50-59`); `location-disclosure.md` says it opens the URL. Needs `url_launcher` (and an Android `queries` entry) or a webview before release.
- F19. Release guards for placeholders. `core/config.dart:10-12` defaults `MAP_TILE_PROVIDER` and `PRIVACY_POLICY_URL` to the literal `[MAP_TILE_PROVIDER]` and `[PRIVACY_POLICY_URL]`, and `MAP_STYLE_URL` defaults to `demotiles.maplibre.org`. Nothing fails a release build that forgets them. Add an assert in `main()` for release mode or a CI step on the release build, and make the disclosure provider name derive from the same decision as the style URL so the text cannot name a different tile server than the one used.
- F20. Docs are stale against the code. `location-disclosure.md` still refers to `AppGate` and `mobile/lib/features/disclosure/disclosure_screen.dart` (now `ui/disclosure/` plus go_router). `privacy-policy.md:32` says "the app does not offer reporting yet" and `tester-guide.md:28` lists reporting and live updates as "not in this build" while `M-phase2.md` says compliance docs were updated and the app now sends free-text reports and opens a WebSocket. Reports contain text typed by the user and are personal data; update the policy and the data-safety answers (bbox is also sent on `/live`) before testers get this build, even if the store text waits for the device test.
- F21. Disclosure acceptance is a device flag (`profile_repository.dart:13`), not per user. Acceptable, but a second user on the phone never sees the disclosure. Consider keying it per user together with B2.

### Architecture and tests

- F22. `apiServiceProvider` reaches into `runRepositoryProvider` and `authRepositoryProvider` from its `onUnauthorized` closure (`providers.dart:68-79`), and those depend on `apiServiceProvider` back. It works only because both reads are lazy (the report notes an earlier cycle error fixed with explicit types). It also makes a service decide about repositories, against "services hold no state and repositories do not depend on each other". Replace with an event stream or callback registered by `AuthRepository` (the B3 fix removes most of this).
- F23. `test/architecture_test.dart:9` returns an empty list when a directory does not exist, so a moved folder makes a rule pass with zero files checked. Assert that each rule scanned at least one file. Also not checked: `domain/` imports `dart:io`, `data/upload/` stays free of Flutter, and `ui` view models do not import `package:flutter/material.dart`.
- F24. `settle()` is a 15 ms real delay (`test/fakes/fakes.dart:16`), used for every ordering assertion; on a slow CI runner this will flake. Prefer awaiting the specific future or `pumpEventQueue()`.
- F25. No test touches `DriftRunStore`, `DriftUploadStore` or `AppDatabase`; all repository tests use `MemoryStore` for both interfaces. Add a small in-memory Drift test (`NativeDatabase.memory()`) for `unfinishedRun` ordering, `fixesFor` ordering by `t`, `discardRun` cascade and `writeUpload` null handling.
- F26. Debug builds default to `http://10.0.2.2:8000` but there is no cleartext/network-security config (grep of `android/` finds none), so Android 9+ will refuse it. Add a debug-only network security config for 10.0.2.2. This also confirms release cannot silently go cleartext.

### Checks that passed (so they are not repeated)

- Token: only in memory, secure storage and the `Authorization` header and the first `/live` message; no `LogInterceptor`, `print` or `debugPrint` anywhere in `lib/`; `allowBackup="false"`; error strings stored in the database come from the server `detail` or Dio messages, not from request headers.
- Raw GPS: leaves the phone only in `POST /runs` (and the home-zone centre and `bbox`, both disclosed). Nothing logs fixes.
- `ACCESS_BACKGROUND_LOCATION`: not in the manifest (the string appears only in an XML comment), `check_manifest.sh` matches the full permission name, fails if no merged manifest is found, and sanity-checks that the scanned file is the merged app manifest. Nit: it scans debug manifests only; add `*elease*` when a release build exists in CI.
- Disclosure is shown before any permission prompt (router redirect plus `disclosure_test.dart` asserts zero requests before the tap); acceptance is stored only after the prompt returns.
- Stop action: the protocol (button id, `sendDataToMain`, `addTaskDataCallback` registered once, `initCommunicationPort` in `main()`) is consistent; the `RunRepository` side is tested with a fake. Still needs the real-device test the report already lists.
- Architecture import rules hold in the files I read; the largest class, `RunRepository`, does three jobs (recorder session, recovery, upload retry) but stays readable.
