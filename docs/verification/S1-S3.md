## VERDICT: REJECT (re-verify after the two BLOCKERS and the FIX list below)

The happy paths and most privacy rules hold (K=3 hiding, home zone, delayed publishing, hard flags, IDOR, JWT, idempotency,
caps, rate limit). Two requirements are not met: account deletion is not consistent (B1) and the leaderboard reveals
unpublished ownership changes at once (B2). There are also several ways to make the API return 500, and a non-idempotent
claim step on task redelivery.

## Findings

### BLOCKER

**B1. DELETE /me is not consistent (privacy rule "removes user, runs, cell_power, fixes ownership consistently").** `server/app/api.py:218-226`, `server/app/processing.py:21-29,159-215`.
The route deletes the user (api.py:220) and runs first, then calls `reassign_after_delete`, which takes the global claims lock and deletes `cell_power` only inside that lock (processing.py:168). Two proven failure modes:
 a. Lock held (busy or dead worker, up to the 120 s TTL): `_acquire` raises `TimeoutError` after 60 s, the request returns 500, and the user is already gone. Test `test_delete_lock_contention_leaves_half_deleted_account`: after the failed call `users=0, cell_power=11, cells owned=11`. A retry gets 401 (token of a deleted user), so the account cannot finish deleting itself; the orphaned GPS-derived data stays until someone cleans it up by hand.
 b. Race with an in-flight run: `process_run_by_id` loads the run (processing.py:50) and only takes the lock later (line 114). If the user's deletion completes in between, the worker still claims cells for the deleted user. Test `test_delete_racing_with_processing`: `cell_power=11, cells owned=11, user=0` after both finished. `build_views` hides ghost owners, but the data is retained and counted in `cell_power`/K-anonymity neighbourhoods.
 Fix direction: take the lock first (or mark the user `deleting` and make the worker re-check the user exists inside the lock before writing), delete the user last, make the whole delete retryable/idempotent (e.g. keep a tombstone until cleanup finishes), never delete the user before cell cleanup succeeds.

**B2. Leaderboard shows unpublished ownership immediately (rule "changes become visible to others only after PUBLISH_DELAY_SECONDS").** `server/app/api.py:165-190`, `server/app/processing.py:91-92` (cache is invalidated on every processed run), `server/NOTES.md` ("Leaderboard shows true owners (not delayed)").
Test `test_leaderboard_leaks_unpublished_ownership` (delay 1800 s): right after A's run, B sees `leaderboard = [{"name":"a","cells":11}]` while `GET /cells` shows B zero cells. Anyone can watch the weekly board and learn when a named user has just finished a run, which the privacy policy says the delay exists to prevent ("so nobody can follow you live"). The board also ignores home zones and K (count only, but it names the user and the count changes with each run). Fix: count only public (revealed) owners, or delay the leaderboard on the same clock, and do not invalidate the cache at processing time.

### FIX

**F1. NaN / Infinity in JSON bodies give HTTP 500 on every float endpoint.** `server/app/models.py:25-29,567-571` plus FastAPI's validation-error handler. For `lat`, `acc` of `/v1/runs` and `lat`, `radius_m` of `/v1/me/home-zones`, literals `NaN`, `Infinity`, `-Infinity` -> 500 (`ValueError: Out of range float values are not JSON compliant`; the 422 body tries to echo `input: nan`). A finite out-of-range value (lat=95) correctly gives 422. Test `test_nan_inf_http_status`. Fix: reject non-finite (`allow_inf_nan=False` on the floats) or a custom `RequestValidationError` handler that drops `input`.

**F2. Integers above int64 give HTTP 500.** `models.py:28,35,36` (`t`, `started_at`, `ended_at` have only `ge=0`). `t=2**63`, `t=2**70`, `ended_at=2**63` -> 500 (`OverflowError: MongoDB can only handle up to 8-byte ints` from `insert_one`, api.py:~121). `2**63-1` and `2**62` are accepted (and `t=2**62` passes through to the engine). Add `le=` bounds (for example year 2100 in ms).

**F3. Claim step is not idempotent on task redelivery, and failures leave runs "processing" forever.** `processing.py:48-104,107-156`, `worker.py:72`.
 a. Cell writes (processing.py:150-153) happen before the run document update (line 89). If the worker dies in between, Celery `acks_late` redelivers, the run still says `processing`, and the credit is added again. Test `test_redelivery_double_credit`: power per cell 0.8182 after the crashed pass, **1.6364** after redelivery.
 b. Any exception other than the engine call (for example a Mongo error mid-claim) propagates; `autoretry_for=(OSError, TimeoutError)` does not cover pymongo errors or redis `ConnectionError` (I checked: `ServerSelectionTimeoutError`, `AutoReconnect` and redis `ConnectionError` are not `OSError` subclasses). Test `test_unexpected_error_leaves_run_processing`: the run stays `processing` (the lock is correctly released). Nothing sweeps stale `processing` runs, so the client polls forever.
 Fix: record per-run claim state (for example store the credit applied per cell with the run id, or apply the claim keyed on run id), retry on `PyMongoError`/`RedisError`, and add a sweeper that marks runs stuck in `processing` for more than N minutes as retryable.

**F4. Freeze handling lets players bypass decay.** `api.py:204-214`, `freeze.py`, engine `faded_power`.
 a. No limit on renewals: a new 30-day freeze can be posted every 29 days, which switches decay off for good. Test `test_chained_freeze_control`: after 116 days, an equal run by B takes 11 cells without freezes and **0** with four chained freezes.
 b. A freeze started after power has already decayed makes it count at full value again while active (engine returns `p.power` unfaded when `freeze_until > now`). Test `test_freeze_resurrects_faded_power_with_control`: 60 idle days, equal run by B takes 11 cells; if A freezes first, B takes **0**. The spec text says "treat fading time as stopped", which a pre-freeze fade should survive. Needs a product decision plus a server rule (cooldown/quota; compute faded power at the freeze start time) and possibly an engine change.

**F5. Raw GPS retention does not match the privacy policy.** `processing.py:56-66,88`, `resources.py:67-74`, `docs/compliance/privacy-policy.md` ("Raw GPS points of a run: [90 days] after upload, then deleted").
 - Accepted runs: fixes are dropped at processing time (shorter than the policy; fine, but the policy should say so).
 - `pending_review`, `implausible_loop` runs are kept (`keep_fixes_for_review`) **with no expiry**: no TTL index, no purge job (runs indexes are only `_id` and `user_id`).
 - Engine failure path (processing.py:57-66) sets `status: rejected` and **never unsets `fixes`** (test `test_engine_failure_policy`: `fixes stored: True`), so raw GPS from errored runs is kept indefinitely too. Stuck `processing` runs keep fixes as well.
 Fix: unset fixes in the error path, add `review_expires_at` plus a TTL index (or a purge task) and make the policy say the same number.

**F6. Other privacy-policy mismatches (state exactly):**
 - Policy "Account deletion ... your ownership of cells (the cells become unowned)". Code (processing.py:184-211) gives each cell to the strongest remaining user and only clears cells nobody else has power in. Either the policy or the code must change.
 - Policy: "Reports: [12 months]". No purge or TTL exists for `reports` (index on `created_at` only). Reports about a deleted user's runs/cells survive deletion (documented in NOTES; policy does not say so).
 - Policy: device integrity signal "checked with Google's Play Integrity service". Server stores `integrity_token` (up to 16 KB) with `integrity_verdict: "unchecked"` (api.py:~110) and never checks it. Policy row is marked PROPOSAL, but the statement is currently false.
 - Policy lists "email address" as collected. The server does not store the email (only `google_sub` and `given_name`/`name`), which is better than the policy; the policy over-states.
 - Policy "Other players cannot see your ... run times": the leaderboard timing leak in B2 is the exception.

**F7. Request-size cap only applies to `Content-Length`.** `main.py:46-51`. A chunked upload skips it: `test_chunked_body_not_capped` sent a 17 KB chunked body with `max_body_bytes=1000` and got 202. The server will buffer and JSON-parse an arbitrarily large chunked body before the 20000-fix 413 check (api.py:99). Caddy has no `request_body max_size` in `deploy/Caddyfile`. Add a streaming size limit (ASGI wrapper) and/or Caddy `request_body { max_size 8MB }`. Also the 413 for >20000 fixes happens after full Pydantic validation of every fix.

**F8. Leaderboard exclusion is keyed on the last claiming run.** `processing.py:148-149`, `api.py:174-177`. When a user re-runs cells they already hold with a flagged (`implausible_loop`) run, `owner_run_id` is re-pointed to the flagged run and all those previously legitimate cells vanish from the board (test `test_laundering_and_collateral`: 11 -> `[]`), and a later clean run on the same cells restores them (-> 11). Exclusion should be per cell origin (or recomputed from review state), not "last run to touch it". Also `excluded` is an unbounded `$nin` list and `runs.review`/`leaderboard_excluded` are not indexed.

**F9. Global claims lock weaknesses.** `processing.py:21-34`. It does have a TTL (`processing_lock_seconds`=120, verified TTL=120 in redis), so a dead worker only blocks for up to 2 minutes. But: the TTL is not renewed (test `test_lock_expiry_midway_allows_overlap`: a second worker acquires after expiry while the first may still be writing), and `_release` is `GET` then `DELETE` (not atomic, so it can delete a lock another worker just took); use a Lua compare-and-delete and a watchdog/extend. DELETE /me turns a lock timeout into 500 (see B1).

**F10. WebSocket authenticates only at connect.** `live.py:30-35,60-80`. A deleted user's open socket keeps receiving frames (test `test_ws_deleted_user_keeps_receiving`: True), and the 30-day JWT is never re-checked. Frames themselves are safe (owner null when hidden, exact keys `{type,cell,owner,mine}`; verified for hidden and home-zone cells). Also no limit on sockets per user, and the token travels in the query string (contract mandated), so Caddy's access log (`log` block in `deploy/Caddyfile`, console format) will record it: filter `token=` from logs.

**F11. Secret/dev-name hygiene.** `auth.py:22,62`, `main.py:28-31`.
 - `DEV_NAME` uses `^...$` with `.match`, and `$` accepts a trailing newline: `dev:abc\n` returns 200 and creates a different user from `dev:abc` (test `test_dev_name_newline_and_odd`). Use `fullmatch`.
 - Only the built-in default secret is refused; `LOOPRUN_JWT_SECRET=x` boots in production mode (test `test_prod_refuses_default_secret_and_accepts_empty_or_short`). Enforce a minimum length (for example 32) when `dev_auth` is off. Also nothing stops `LOOPRUN_DEV_AUTH=1` together with a real secret in production; add a startup warning/refusal if `google_client_id` is set and dev auth is on.

### NOTE

N1. **google_verify (auth.py:46-51) matches google-auth 2.62.1.** `verify_oauth2_token` checks signature (RS256 with Google certs), expiry, audience and issuer; matrix from `test_google.py` (real library, stubbed certs): valid ok; wrong aud / missing aud / aud list containing ours -> rejected; wrong iss -> `GoogleAuthError`; missing iss -> `KeyError` (caught by the broad `except`, 401); expired -> rejected; missing exp -> rejected; `alg none` and HS256-with-public-cert -> `Unsupported signature algorithm`; garbage -> rejected. A token with no `sub` passes the library but `identify` returns 401 (auth.py:73-75). Remarks: (a) `email_verified` is not checked, which is fine only because email is not used for identity; keep it that way. (b) `clock_skew_in_seconds` defaults to 0: a token issued a few seconds "in the future" relative to the server clock is rejected (`iat` +5 s -> "Token used too early"); pass `clock_skew_in_seconds=10`. (c) A fresh `requests.Request()` per call fetches Google's certs from the network on every sign-in (no caching). (d) `LOOPRUN_GOOGLE_CLIENT_ID` must be the Web (server) client ID the Android app requests tokens for, otherwise every audience check fails; RUNBOOK should say which. No test in the repo covers this path; my matrix is not committed to `server/`.
N2. **JWT (auth.py:25-44)**: pinned `algorithms=["HS256"]`, requires `exp` and `sub`; verified rejects: no token, malformed, Basic scheme, `alg none` (library-made and hand-made), wrong secret, HS512, expired, no `exp`, token of a deleted user (also after re-registering the same dev name), non-string `sub`. No revocation/logout (30-day TTL). Dev token `dev:x` with `dev_auth=False` -> 503 (no client id) or 401 (client id set); verified.
N3. **Mongo injection**: all query values come from typed models, `UUID`, regex-checked dev names, or server-generated ids; JWT `sub` must be a string. Probed: operator dicts/lists as `id_token`, as report `target_id`, JWT with object `sub`, odd path ids -> 422/404/401, never reaches a query. No user-controlled dict keys.
N4. **Unbounded/expensive queries.** `GET /cells` returns up to 20000 docs (`cells_max_results`, silently truncated) and then queries `cell_power` for `37 x` cells in chunks of 4000 (cellview.py:249-258); there is no rate limit on GET /cells or WS connects. In mongomock 4921 cells took 0.41 s; real cost will be dominated by Mongo round trips. Leaderboard aggregates over all `cells` every 60 s cache miss. Each Celery task builds a new Mongo and Redis client (worker.py:64). Each WS event spawns a task that sleeps up to the delay (capped at 5000 per socket).
N5. **Indexes vs the plan.** Present: `users.google_sub` unique, `runs.user_id`, `cell_power(cell,user_id)` unique, `cell_power.user_id`, `cells(lat,lng)`, `cells.owner_id`, `reports.created_at`. Missing: `cells.public_owner_id` / `cells.pending_owner_id` (the `$or` in `reassign_after_delete` becomes a collection scan), `runs(review, leaderboard_excluded)`, `cells.owner_run_id`, any TTL index. (The plan document was not in the repo, so "versus the plan" is judged against the contract/BOARD and the task text.)
N6. **Rate limit** is a fixed window (api.py:67-76): 3 uploads just before a boundary plus 3 just after were all accepted with limit 3 (`test_rate_limit_boundary_burst`: six 202). Per-user, resets per window, 429 carries `Retry-After`, invalid (422) bodies and repeats of a stored id do not consume quota; `incr` then `expire` is not atomic (a crash between them leaves a stale key; harmless since the window is in the key name).
N7. **K-anonymity details.** Verified: with 2 distinct users in the 3-ring neighbourhood every non-mine cell is `hidden:true, owner:null`; with 3 the names appear; a third user ~6 km away does not count. Weaknesses inherent to the design: the count uses unpublished power (a brand-new run can reveal a neighbour's name before its own cells are public), and free accounts can be Sybil'd (two throwaway accounts running nearby push K to 3).
N8. **Concurrent duplicate uploads**: 6 threaded and 8 truly concurrent (asyncio/httpx) requests with one id all returned 202, exactly 1 run document, exactly one credit. Minor: the loser of the insert race still consumed one rate-limit slot, and if the winner's enqueue fails and deletes the run (api.py:~129-134) the loser has already been told `processing`.
N9. **Contract diff** (generated OpenAPI vs `docs/CONTRACT.openapi.yaml`, script `oas_diff.py`):
 - All 9 REST operations exist with the contract's methods under `/v1`; success codes match (200/202/204). Generated path `/v1/runs/{run_id}` vs contract `{id}` (name only). `/live` is a WebSocket and is not in the generated OpenAPI (expected; implemented at `/v1/live`, close codes 4401 for bad token, 1008 for bad bbox).
 - Generated spec documents `422` on most routes, but not the contract's `413`/`429` (POST /runs), `401` (POST /auth/google and the secured routes), `404` (GET /runs/{id}); these are returned at runtime (verified) but are undeclared. Contract does not list `409` (cross-user duplicate id), `422` for `/cells` bbox, or `503`; the server returns them. Extra routes `/healthz`, `/v1/healthz`.
 - Schema shapes match (UserRef, Session, RunUpload required fields, RunStatus, Cell/CellOut incl. `hidden`, Flag, leaderboard, freeze). Server is stricter than the contract: lat/lng ranges, `t>=0`, `acc` 0..100000, `ended_at>=started_at`, report `target_id` 1..100 and `reason` 1..500, `integrity_token` max 16384. `fixes` has no `maxItems` in the generated schema on purpose (413 instead of 422). Empty `fixes` is accepted and ends `accepted` with 0 cells.
 - `GET /runs/{id}` with a non-UUID id returns 422 (contract says `format: uuid`), not 404.
N10. **Behaviour verified OK** (tests passed): IDOR (B gets 404 on A's run; B reusing A's run id gets 409 and A's run is untouched); client-claimed `cells`/`owner`/`status`/`cells_claimed` in the body are ignored; 20000 fixes accepted, 20001 -> 413; Content-Length over cap -> 413; bbox: >0.2 deg, min>max (lng and lat), NaN/inf/1e400, wrong arity, missing -> 422; zero-area box 200; reversed/duplicate-timestamp fixes processed without error; started_at after ended_at -> 422; hard-flag runs (mock, vehicle_speed/teleport) -> `pending_review`, 0 cells, no `cell_power` rows; leaderboard excludes `pending_review` and `implausible_loop` runs; equal power does not take a cell; delayed publishing (nothing for others at 1799 s, visible after 1801 s, takeover also delayed, owner sees own at once); home zone hides owner for others and not for the owner; delete with another user's power re-owns, with none clears, leaves no `cell_power`, `owner_id`, `public_owner_id`, `pending_owner_id` for the deleted user and a second DELETE returns 401; freeze limits (31, -1, 1.5 -> 422); reports validation and 20/h limit; WebSocket without/invalid/deleted-user token and missing/huge/NaN bbox rejected, header token not accepted, frames never carry a hidden owner (hidden by K and by home zone).
N11. **Secrets/logging**: no secrets in code except the dev default JWT secret guarded in `main.py`; prod compose does not set `LOOPRUN_DEV_AUTH`; the logging formatter says never log coordinates and the processing/auth logs contain ids and counts only (an `account_deleted` log has no user id). Run ids and flag codes are logged.
