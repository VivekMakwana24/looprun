## New findings
### FIX
**N1. A `deleting` account stays visible.** After DELETE /me returns 503, `GET /cells` (other viewer) still shows the owner name and `GET /leaderboard/weekly` still lists the user, until deletion completes (`cellview.py` `build_views`, `api.py` `leaderboard`, `_public_counts`). A user who asked for deletion and got 503 stays public indefinitely if the client never retries (no sweeper for `deleting` users). Hide `deleting` owners in both, and finish stale `deleting` accounts from a job.
**N2. Deleted user's id survives in other users' `run_claims`; the collection is never cleaned.** `processing.py` `_plan` stores per-cell `owner` (the current owner, possibly another user) plus lat/lng for every processed run; `delete_account` deletes only the deleting user's own plans. Test `test_deleted_users_id_survives_in_other_users_run_claims`: after A deletes, 11 occurrences of A's id remain in B's plan. `run_claims` also has no TTL: 5 accepted runs = 5 docs (~3.9 kB each, grows with cell count; 16 MB doc limit far away). Fix: delete the plan when the run is finished (keep only while `applied` is false), or add a TTL.
**N3. Lock set has no watchdog while still acquiring.** `locks.py:70-82`: watchdog starts after the last lock. With ttl 2 s, a set waiting 3 s for its second key returns "acquired" while an intruder holds the first (`test_first_lock_expires_while_waiting_for_second_and_nobody_notices`), and `check()` passes until the first watchdog tick (TTL/3). Needs wait > TTL (defaults 60 s vs 30 s) behind a live slow holder, so rare; start the watchdog at the first acquire or extend all held locks right after acquire.
**N4. Freeze start/end write cell_power without locks or guards.** `freeze.py:34,85` and the freeze route take no lock and use bare `_id` filters; `settle_expired` inside a claim also rewrites rows of users in regions the claim has not locked. A claim write landing between the read and the update is overwritten (unit test with an interleaved write: credit 9.0 replaced by 0.059). Window is milliseconds (user freezes right after uploading), but a lost credit or reset time is possible. Guard the update with `updated_at`/`power` equality or take the user lock plus regions.
**N5. Zombie runs; sweeper still absent.** A process death between `runs.insert_one` and `run_fixes`/enqueue (`api.py:119-141`, only `Exception` is handled) leaves a `processing` run; a same-id retry returns 202 `processing` forever and nothing re-enqueues. Same for a lost Redis queue. Make the duplicate branch re-enqueue (or delete) a run that is `processing` with no fixes or older than N minutes, or add a periodic sweeper.
**N6. Upload racing account deletion leaves an orphan run.** A request authenticated before `deleting` was set but inserting after `users.delete_one` creates a run and fixes for a missing user (simulated with a stale dependency override: run stays `processing`, fixes live 30 d). Window is tiny. Re-check the user after the insert and delete the run if gone.

### NOTE
N7. WebSocket with the query token or a bad bbox closes BEFORE accept, so a real client sees HTTP 403 on the handshake, not 4401/1008 as the contract says (real uvicorn run). First-message path gives 4401 correctly. Pre-auth first message is read up to the library limit (2 MB tried).
N8. `LockLost`, Mongo or other errors inside DELETE /me give 500 (only `LockTimeout` -> 503). Retry still works (all 29 fault points resumable).
N9. Eager Celery re-raises `Retry` out of `enqueue_run` (503 in tests), so real retry timing is only verified through a manual retry loop, not the Celery runtime.
N10. A run that fails after its plan was partly applied is `rejected` yet keeps the credit/ownership already written (documented by builder).
N11. Leaderboard shows owners whose cells are K- or home-zone-hidden on the map (count only; documented). Viewer's own entry is live, so their own count drops at once on a takeover while /cells still shows them as owner. Leaderboard fetches all owning users and caches all counts in Redis (scale).
N12. `_user_regions`/`_reassign_cells` build one `$in` list of all cells of the user (16 MB limit at roughly 600k cells; chunk it). No sockets-per-user cap; one sleeping task per event per socket.
N13. LockSet relies on callers passing keys in sorted order (both callers do); a defensive sort inside LockSet would remove the foot-gun.
