# Verification report: O1 (DevOps) and C1 (Compliance)

Verifier: independent agent, 2026-11-03. Reviewed state: `ci.yml` and `release-android.yml` as modified at 18:06 (the builder changed both while I was reviewing; I re-read and re-linted the final versions), every other file as of 18:01 or earlier. No reviewed file was edited and nothing was committed.

## Verdict: REJECT (O1 and C1 both)

The core of O1 is sound: Dockerfile, both compose files, Caddyfile, `ci.yml`, `deploy.yml` and the shell scripts all lint and validate clean, and the deploy gate is correct. Three BLOCKERs stop acceptance:

- O1: the release workflow cannot produce a correctly signed or correctly configured AAB (findings 1 and 2).
- C1: the central privacy claim, "location only while recording a run", is contradicted by the mobile code (finding 3).

The FIX items are mostly C1 statements that are false or not yet implemented. If findings 1 to 3 are fixed and the C1 FIX items are applied (or the matching engineering work lands), this becomes ACCEPT WITH FIXES.

## Findings

### BLOCKER

1. **Release signing is never consumed.** `.github/workflows/release-android.yml:38-46` writes `android/key.properties` and the keystore, but nothing makes Gradle read them. `mobile/tool/patch_android.sh:15` only patches `minSdk`, and `bootstrap.sh` takes the stock `flutter create` Gradle files. A repo-wide grep for `signingConfig` or `key.properties` finds only the workflow and `docs/RUNBOOK.md:134`, which admits the dependency. From memory (cannot run Flutter here), the stock template signs `release` with the debug key. The job would therefore go green and upload `looprun-release-aab` signed with the debug key, which Play rejects. Fix: have `patch_android.sh` inject a `signingConfigs.release` that reads `key.properties` and set `buildTypes.release.signingConfig`, then add a workflow step that fails if the AAB certificate is "Android Debug" (`keytool -printcert -jarfile`).

2. **Release build has no `--dart-define`s.** `release-android.yml:60-62` runs a bare `flutter build appbundle --release`. `mobile/lib/core/config.dart:3-11` then defaults to `API_BASE_URL=http://10.0.2.2:8000` (emulator loopback, cleartext), an empty `GOOGLE_SERVER_CLIENT_ID` (Google sign-in cannot work) and the MapLibre demo tile style. The AAB would build but not work, and the Data safety answer "encrypted in transit: Yes" (`data-safety-answers.md:12`) would be false for it. Fix: pass `API_BASE_URL`, `GOOGLE_SERVER_CLIENT_ID` and `MAP_STYLE_URL` from repository variables or secrets, and fail the job if any is empty or the URL is not `https://`.

3. **C1 states that precise location is used only during a run; the app also reads it outside runs.** The claim is made without qualification at `privacy-policy.md:20` ("Only while you are recording a run. Not before you press start"), `location-disclosure.md:19`, `listing.md:27`, `foreground-service-declaration.md:14` ("Location is not collected outside an active, user-started run") and `tester-guide.md:46`, and the shipped disclosure screen says the same (`disclosure_screen.dart` "Only while a run is active"). But `mobile/lib/features/map/map_screen.dart:38` calls `getCurrentPosition(accuracy: high)` to centre the map whenever the map opens (and the visible bbox is then sent to the server), and `mobile/lib/features/profile/profile_screen.dart:50` does the same to place a home zone, whose centre is stored on the server. Either change the app (for example centre the map on a coarse or last-known position and let the user type or pick the home zone), or reword all five documents and the disclosure screen to say what actually happens. Play compares policy and disclosure text with observed behaviour.

### FIX

4. **Account deletion is described wrongly.** `privacy-policy.md:67` says the cells "become unowned". `server/app/processing.py:159-195` (`reassign_after_delete`) gives each cell to the strongest remaining player and only drops cells nobody else has power in. `listing.md:31` ("removes your runs and your cells") and the in-app dialog (`profile_screen.dart:81`) are looser but should say the same thing. The rest of the deletion claim is correct: `DELETE /me` removes the user, runs, reports they filed, cell power and home zones (`api.py:217-226`).

5. **The 90-day raw GPS retention is not implemented, and the table is inaccurate in the other direction too.** `privacy-policy.md:20,58` says raw points are stored after the upload and deleted after [90 days]. In code, `processing.py:88` drops `fixes` immediately for accepted runs and keeps them only for runs needing review (`config.py:40`), with no TTL: `resources.py:68-74` creates no expiry index, so flagged runs keep raw GPS until the account is deleted. The policy marks this as a PROPOSAL, so this is the engineering work the policy itself says is needed (add a TTL or purge job for flagged runs and for reports), or change the text to match. The same goes for "reports [12 months]" (`:61`).

6. **Crashlytics, Firebase and Play Integrity are described as collected but are not in the app.** `mobile/pubspec.yaml` has no Firebase or Crashlytics dependency (only `geolocator`, `flutter_foreground_task`, `google_sign_in` among the relevant ones). `mobile/NOTES.md:27` says the integrity token is sent as null. Affected: `privacy-policy.md:27` (an unconditional row), `:24`, `:46`, `:62`; `data-safety-answers.md:32-34`; `closed-test-checklist.md`/`RUNBOOK.md:118` (`google-services.json`, `release-android.yml:47-53`). Remove these rows until the SDKs ship, or add the SDKs. Declaring data you do not collect is safer than the reverse, but the policy must still be true.

7. **Email is declared as stored; the server does not store it.** `privacy-policy.md:22` and `data-safety-answers.md:28` say the Google email is collected. `server/app/auth.py:76-97` stores only `google_sub` and the given/display name. The email is still transmitted inside the ID token, so the Play "collected" answer is defensible, but the policy should say precisely what is stored. Also note the stored name is Google's `given_name` (first name) in preference to the full name (`auth.py:76`), and it is shown to other players.

8. **A third party sees map requests and is not disclosed.** `mobile/lib/core/config.dart:9-11` defaults the style to `https://demotiles.maplibre.org/style.json` (a demo server, not for production). Tile requests expose device IP and the viewed area to the tile host. `privacy-policy.md:44-47` (service providers) and the Data safety sheet omit it, and `location-disclosure.md:23` / `listing.md:30` say nothing is shared. Pick a production tile provider, name it in the policy, and decide how the Data safety form treats it.

9. **Foreground-service declaration claims things the code does not do.** `foreground-service-declaration.md:9` lists a notification "with a Stop action"; `mobile/lib/features/run/foreground_service.dart:54-60` sets no notification buttons. Also `:22` suggests presets and says "if the list has a fitness entry, prefer that". Google's page (13392821) lists exactly three presets for the location type: background location updates (user-initiated sharing), background location updates (navigation, for example ride tracking) and geofencing, so name the navigation/ride-tracking one or enter the use case manually.

10. **Features advertised or tested that the mobile app lacks.** `mobile/NOTES.md:27` ("Not done: WebSocket /live, reports") and a grep of `mobile/lib` (no report UI) show that reporting and live updates are missing. Yet `listing.md:34,37` ("Live map", "Report a run or a cell") and `tester-guide.md:23` (step 9, Report) rely on them. Remove them from the copy and the test script until M2 delivers them.

11. **`location-disclosure.md` does not match the shipped disclosure.** The doc (`:7-9,29`) says: shown on the first Start run, a "Not now" button that leaves the app usable, a "do not share your location" sentence and a Privacy Policy link. The app (`mobile/lib/features/disclosure/disclosure_screen.dart:30-90`, `app.dart:23-36`) shows a gate screen right after sign-in with different wording, no sharing statement, no policy link, and a single decline path that signs the user out. Pick one and make the documents and app identical. `location-disclosure.md:3` also says the policy could not be opened; I opened it, see below, so the "Unverified" tag can be updated (apart from "uses the user's language", which I did not find in the fetched text).

12. **Deploy host-key handling falls back to trust-on-first-use.** `deploy.yml:68-73` accepts an unset `LIGHTSAIL_HOST_KEY` with `ssh-keyscan` and only a warning, and `RUNBOOK.md:112` documents that. For a deploy credential that is the weak point. Make `LIGHTSAIL_HOST_KEY` mandatory (add it to the loop at `deploy.yml:60`) and add `-o StrictHostKeyChecking=yes -o BatchMode=yes` to the `ssh` call at `:76`. What is good: the key is only ever written to a 0600 file via `printf`, never echoed; ssh's default `ask` fails closed in a non-interactive run; `IdentitiesOnly=yes` is set.

13. **The production JWT secret is not generated, and nothing stops the placeholder from being used.** `deploy/setup-lightsail.sh:98` writes `LOOPRUN_JWT_SECRET=CHANGE_ME_long_random_string` while the Mongo password is generated (`:84`). The server rejects only its own default constant (`server/app/config.py:14`, `main.py:29-30`), so the placeholder is accepted and anyone could forge session tokens. Generate it with `/dev/urandom` like the Mongo password, and add `${LOOPRUN_JWT_SECRET:?}` (and a non-placeholder check) to `docker-compose.prod.yml`. As defence in depth, also set `LOOPRUN_DEV_AUTH: "0"` explicitly under the prod `environment:` (it overrides anything added to `env_file` later).

14. **CI claims real Redis and Mongo, but the server tests use fakes.** `ci.yml:18-41` starts both services and exports `LOOPRUN_MONGO_URL`/`LOOPRUN_REDIS_URL`, yet `server/tests/conftest.py:11,13,88` uses `fakeredis` and `mongomock-motor` and never reads those variables. `RUNBOOK.md:140` and DECISIONS D5 therefore overstate. Either add a small integration test that honours the variables (unique-index behaviour and Celery against real Redis are worth having) or remove the services and the sentence.

15. **`make validate` does not check what it says.** `Makefile:32` runs `bash -n deploy/setup-lightsail.sh deploy/backup.sh`; `bash -n` treats the second file as an argument, so `backup.sh` is never checked (I confirmed this with a deliberately broken second file: exit 0). Loop over the files. `.PHONY` also lists `prod-config` (`Makefile:1`), which has no target, so `make prod-config` silently does nothing. CI has no `docker compose config` step, so the board criterion "compose file valid" is not enforced anywhere automatically; consider adding one with a dummy env file (as I did).

16. **Tester guide route length can trigger a rejected loop.** `tester-guide.md:18` asks for "at least 400 metres around a block". `ENGINE_SPEC.md` sets `min_loop_area_km2 = 0.01` (10,000 m²); a square with a 400 m perimeter is exactly that area, and any real, irregular 400 m loop is below it, giving `loop_rejected_small`. Ask for roughly 1 km or more. Same file `:42` says "Android 8+" while `patch_android.sh:13-15` sets minSdk 24 (Android 7).

17. **Placeholders are only partly listed.** `privacy-policy.md:87` lists five placeholders, but the file also has `[90 days]`, `[12 months]`, `[14]` (`:58-63`), and other files have `[OPT_IN_LINK]`, `[TEST_START]`, `[TEST_END]`, `[FEEDBACK_CHANNEL]`, `[PRIVACY_POLICY_URL]`, `[CONTACT_EMAIL]` (`tester-guide.md:9,11,30,46`; `listing.md:77`). There is no single pre-launch list across the compliance folder. Also `[DELAY]` can be filled with "30 minutes": the default is 1800 s (`config.py:45-47`) and prod compose does not override it.

I checked them against `server/app/config.py`: `LOOPRUN_MONGO_URL` (:22), `LOOPRUN_REDIS_URL` (:25), `LOOPRUN_DEV_AUTH` (:32), `LOOPRUN_JWT_SECRET` (:33), `LOOPRUN_GOOGLE_CLIENT_ID` (:35) all match the compose files and `.env` template. Remove the caveat.

19. **Dockerfile review (line by line):** build context is the repo root and the paths are right (`COPY engine`, `COPY server`, `pip install ./engine ./server` in a venv, then copied to a clean runtime stage); non-root user (uid 10001); no secrets or `ENV` credentials; HEALTHCHECK uses `python`/`urllib`, which exists, against a real `/healthz` that returns 503 when Mongo or Redis is down; CMD is correct (`uvicorn app.main:create_app --factory`) and the worker override matches `app.worker:celery_app`. Minor: use `USER 10001:10001` (DL3066); `/app` is root-owned so the user cannot write there (fine today); base images are tags, not digests; `--forwarded-allow-ips "*"` is only safe because prod api has no published port (dev publishes on 127.0.0.1 only).

20. **Prod compose details.** `docker-compose.prod.yml:12` hardcodes `env_file: /opt/looprun/.env`, so a different `APP_DIR` breaks it; the env file also injects `MONGO_PASSWORD` and `LOOPRUN_DOMAIN` into api/worker (harmless, but unnecessary); Caddy waits for `api` only to be started, not healthy; no Mongo cache cap on a small host (`wiredTigerCacheSizeGB`). Mongo and Redis are unexposed and on a private network, and Redis uses `noeviction` with AOF, which is right for a Celery broker.

21. **Workflow hygiene.** Actions are pinned by tag (`@v4`, `@v2`), not SHA; Flutter `channel: stable` is unpinned. `deploy.yml` has no automatic rollback after a failed health check (`:86-94`; documented in the runbook as manual). `release-android.yml` has no CI gate and can be dispatched from any ref. The `GITHUB_SHA` on a tag push is, as I understand it, the commit SHA; I could not verify that without a runner. Gate logic otherwise checks out: it requires `origin/main` ancestry (`deploy.yml:30`) and a successful `ci.yml` run for the exact `$GITHUB_SHA` (`:38-39`), the deploy job `needs: gate` (`:48`), and the host checks out that same SHA (`:81`). A rapid second push cancels the first CI run (`ci.yml:7-9`), which makes the first commit undeployable until re-run; acceptable.

22. **Scripts.** `backup.sh:15-18` leaves a partial `*.tmp` if `mongodump` fails (the `mv` is skipped, correctly); backups are local-only (documented). `setup-lightsail.sh:85-102` writes `.env` with the default umask and then `chmod 600` (a short window). `RUNBOOK.md:14` suggests `curl raw.githubusercontent.com/...` which fails for a private repo (the same line offers `scp`). The ENV `.env` template, cron line, restore command and password-rotation steps read correctly; they are unexecuted.

23. **Privacy statements that are consistent with the code.** Delayed publishing is implemented for other viewers, with the new owner seeing changes at once (`config.py:45`, `cellview.py:50`, `live.py:3-6`). Home-zone cells never show the owner's name (`cellview.py:79-80`, same logic for WebSocket pushes). Other players cannot see routes, GPS points or run times via any API. Max five home zones, freeze up to 30 days, delete account all exist in server and app. The manifest has the location foreground-service type, `FOREGROUND_SERVICE_LOCATION`, and no `ACCESS_BACKGROUND_LOCATION`. Backup retention of 14 days matches `backup.sh`.

24. **Behaviours the copy leaves out.** The server hides owner names unless at least 3 distinct users hold power nearby (`config.py:50-51`, `cellview.py:80`), so `listing.md:20` ("Cells you own show your name") is not always true for other viewers. The weekly leaderboard counts are not delayed (`api.py:163-190`, 60 s cache), so `privacy-policy.md:35` ("so nobody can follow you live") holds for the map, not for leaderboard movement. The `profile_screen.dart` toast says "Runs inside it stay hidden"; the server hides cell ownership, not runs.
