## Findings

### FIX

1. **Freeze semantics reveal faded power as full power** (`engine/looprun_engine/ownership.py:20-21`, NOTES.md #10). While `freeze_until > now`, `faded_power` returns `p.power` unfaded, including fade that had already accrued before the freeze began. Measured: stored power 10.0, updated day 0: at day 30 unfrozen it is 3.20; with `freeze_until` day 31 it is **10.00**; at day 32 (freeze expired) it is **2.90**. So a freeze started late raises a user's power back to its original value, then power drops at expiry. `apply_claim` also builds the stored power from that unfaded base (`ownership.py:51`: faded base 10.0 + credit 1.0 stored as 11.0). The engine itself is internally consistent and monotonic, but a freeze is not a "stopped clock". What the server must do:
   - Pass `freezes` only for users whose `freeze_until > now` (the server's `active_freezes` appears to do this; confirm that expired freezes are excluded).
   - On freeze **end** (explicit, replaced, or lazy expiry), shift each of that user's `cell_power.updated_at` forward by the frozen time. `server/app/freeze.py:25` does `updated_at + end - max(updated_at, started)`, which is correct: for a row last updated before the freeze start it shifts by `end - started`, so fading resumes from where it was at freeze start. I checked the arithmetic against `faded_power`; it is consistent.
   - On freeze **start**, to avoid the inflated-while-frozen window (and an owner flip caused by it), rebase: for each of the user's cells already past grace, write `power := faded_power(now)` and `updated_at := now - grace_days*86400000`, so the value shown during the freeze equals the value at freeze start and fading would resume at the correct point after the end shift. Without this, ownership comparisons during a freeze use the unfaded power. Needs a decision from the product owner if the inflation is acceptable.
   - Enforce `max_freeze_days` on the server; the engine does not use it anywhere.
2. **Zero-credit claim resets grace** (`ownership.py:49-52`). For a user with an existing entry, `credit == 0` still stores `power=faded` and `updated_at=now`, which restarts the 7-day grace for free (NOTES #11 says this is deliberate and literal). The server should not call `apply_claim` when `credit == 0` (e.g. `moving_seconds == 0`), or this is a free grace refresh. Low likelihood today since a run with loops has moving time, but the guard is one line.

### NOTE

3. `implausible_loop` and `too_few_fixes` are soft, so they still award cells and status stays `accepted` (spec behaviour 4). Measured: a 6 km square (36 km2, perimeter 24 km) gives 2624 cells with only `implausible_loop`; a 17-fix run closing a 400 m loop gives 11 cells with `too_few_fixes`. Matches spec, but the server may want to surface these for review. Product decision.
4. `vehicle_speed` is never evaluated when the whole run (or the remaining tail) spans less than `sustained_window_s` (`flags.py:36-39`; NOTES #9). A 29-second run at 12.4 m/s raised no flag (measured); 10 m/s for 30 s then walking: no flag. Only `teleport` (hops above 12.5 m/s) covers short bursts. Consistent with the spec's wording; low risk because short runs cannot make a valid loop anyway.
5. Perimeter and speed use the noisy cleaned path, so GPS noise inflates length: my 400 m square with 3 m noise measured 1922 m against 1600 m true (+20%). The effective `max_loop_perimeter_km` is therefore about 21 km for noisy tracks. No smoothing (NOTES #2) is spec-allowed.
6. Near-closure checks the last point against earlier **vertices** only, not segments (`loops.py:47-52`), and ignores vertices within `closure_tol_m` of path length before the end (`loops.py:48`, a guard not in the spec, documented in NOTES #3). With 100 m fix spacing a mid-segment closure still worked in my test; larger gaps between fixes could miss one. Acceptable.
7. `process_run` and `faded_power` have no guard against `halflife_days <= 0` or `sustained_window_s == 0` (`ownership.py:26` would raise `ZeroDivisionError`). Config comes from the server, so keep it validated there.
8. `effort_credit` uses `moving_seconds` only: a faster run earns less credit (NOTES #12). The simulation still shows steady beating a single run, as the board requires. Worth a product-side check that "faster" users are not unintentionally penalised.
9. Loops under about 1 cell with no cell centre inside get the single cell holding the representative point (`loops.py:25-28`, NOTES #5). A 100x100 m loop (0.01 km2) therefore earns one full cell (0.0152 km2). Deliberate and sensible.
10. Hard flags use all raw fixes for the mock check, including fixes dropped by cleaning (`pipeline.py:19`). Good for anti-cheat; stated so the server expects `pending_review` for a mock fix even when it is the only bad fix.
